Wound care · reference architecture

API serving with FHIR, HealthLake and Athena

Reference architecture for a wound-care read API. The service in this repository runs on synthetic records. The latency figures below are design targets and have not been measured on a live deployment.

Excerpt

Partner and patient apps call a FHIR R4 API through API Gateway. AWS HealthLake serves the reads and bulk-exports NDJSON into an S3 lake. Glue catalogs the lake, and a query builder renders a reviewed SQL template for Athena. A SageMaker endpoint can add a healing-risk score on the same API.

What this flow does

Serves wound-care data two ways from one clinical record: a FHIR R4 read API, and operational analytics through governed metric templates. A risk score can be attached for a clinician to review.

Key steps

  1. A FHIR client calls API Gateway.
  2. API Gateway authorises the call and routes reads toward AWS HealthLake (FHIR R4).
  3. HealthLake serves the read and can bulk-export NDJSON.
  4. The export lands in the S3 lake (raw NDJSON, then Parquet).
  5. A Glue job and crawler register the tables in the Glue Data Catalog.
  6. The NestJS service sends a structured request (metric, dimensions, filters) to the query builder. The builder looks up the metric in the semantic mapping and renders a reviewed SQL template.
  7. Athena runs the statement in a per-tenant workgroup. A SageMaker risk score can be added to the clinical response.

AWS services

API Gateway, Lambda, ECS Fargate, AWS HealthLake, S3, Glue (ETL, Data Catalog), Athena, Neptune, SageMaker (endpoint, Feature Store), Lake Formation, IAM, KMS, CloudTrail.

External systems

Partner or patient FHIR apps, and the wound-care system of record.

Deterministic query templates

  • Input is structured: {metric, dimensions[], filters{}, time_range}. Optional search text maps to a metric through a synonym dictionary.
  • The semantic mapping records metric, table, column, and allowed dimensions, with an owner for each metric.
  • Each metric has a reviewed SQL template and fixture queries.
  • Guardrails: allow-listed tables and columns, tenant and facility predicates always injected, row and byte-scan limits.

Security by design

  • IAM least privilege per service; Lake Formation column permissions on PHI.
  • KMS customer-managed keys for HealthLake, S3, Neptune, SageMaker.
  • Audit log of every PHI read; S3 Object Lock for audit records.
  • De-identified, synthetic data for model training and demos.
